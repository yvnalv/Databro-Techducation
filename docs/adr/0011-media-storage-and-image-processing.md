# ADR-0011 — S3-compatible media storage, with images re-encoded on upload

Status: Accepted
Date: 2026-08-16
Deciders: Project owner

## Context

The Media module is the last unbuilt Phase 1 module, and two shipped features are dead without it:
the editor's image block has no way to get an image, and `SeoMetadata.OgImageMediaId` can never be
set, so every share card falls back to nothing.

Three decisions have to be made together, because they constrain each other:

1. **Where bytes live.** DigitalOcean Spaces in production (per CLAUDE.md), MinIO locally — MinIO is
   already running in Compose.
2. **How responsive variants are produced.** The roadmap calls for them; Core Web Vitals on an
   image-heavy article depends on them.
3. **What we accept from an authenticated uploader.** File upload is the single most abused endpoint
   shape on the web, and "an Author is a trusted user" is not a security model.

## Decision

### Storage: one S3 adapter for both environments

`IMediaStorage` in Media.Application, implemented once over the AWS SDK for .NET. Spaces and MinIO
are both S3-compatible, so one adapter with a different endpoint and credentials covers development
and production. Nothing above Infrastructure learns that S3 exists.

Storage keys are **generated by us** — `media/{yyyy}/{MM}/{guid}/{variant}.{ext}` — and never derived
from the client's filename. The original filename is stored as metadata for display only. A
client-supplied path is a directory-traversal bug waiting to happen, and a client-supplied extension
is a content-type bug waiting to happen.

### Images are re-encoded, never passed through

An upload is decoded with **ImageSharp** and re-encoded before anything is stored. The bytes that
land in the bucket are bytes we produced.

This is the security decision, not a quality one. Validating an upload and then storing the original
still stores the original: a polyglot file that is a valid JPEG *and* a valid HTML document or ZIP
archive passes every header check and is then served from our domain. Re-encoding destroys the
non-image portion because it never survives a decode/encode round trip. It also strips **EXIF**,
which routinely carries GPS coordinates — a privacy leak an author would never expect from dragging
a photo into an editor.

Format is decided by **sniffing magic bytes**, not by the `Content-Type` header or the extension;
both are attacker-controlled.

### Variants are generated in a Hangfire job

The upload request stores the original, records the asset with `ProcessingStatus = Pending`, and
returns. A background job produces the width variants and marks the asset `Ready`.

Resizing four variants of a large photograph is seconds of CPU. Doing it inline makes the editor's
upload button feel broken, holds a request thread, and gives no retry when it fails. Hangfire already
runs in this host for scheduled publishing, so this adds a job, not a dependency.

The cost is a **visible pending state**: an image is usable at full size immediately but has no
`srcset` until the job finishes. The API reports `processingStatus` so the CMS can show it rather
than the reader seeing a broken layout.

### Limits, and what they are for

* **10 MB** per file. Large enough for a photograph off a phone, small enough that a decode cannot
  become a denial of service.
* **Dimension cap before decode.** ImageSharp is asked for the image's header first and the file is
  rejected on dimensions alone. This is the *decompression bomb* defence: a 100 MB PNG that
  decompresses to 60,000 × 60,000 pixels is a few hundred KB on the wire and ~14 GB in memory. A byte
  limit alone does not catch it.
* **JPEG, PNG, WebP, GIF in; JPEG, PNG or WebP out.** No SVG — SVG is XML, executes script, and
  cannot be sanitised by re-encoding. If vector assets are ever needed they get their own decision
  and their own sanitiser.

## Alternatives considered

* **Store the original untouched, generate variants at the CDN edge** (Spaces + an image CDN). Less
  code and no processing job. Rejected for Phase 1: it stores attacker-supplied bytes on our domain,
  keeps EXIF, and makes local development depend on a service MinIO does not provide.
* **Synchronous variant generation.** Simpler — no job, no pending state. Rejected: a slow upload on
  every large image, a request thread held for seconds, and a failed resize that cannot be retried.
* **A separate image service (imgproxy/thumbor sidecar).** Better at scale and language-agnostic.
  Rejected as premature: another container to run and secure for a workload one library handles.
* **ImageSharp vs. SkiaSharp vs. Magick.NET.** ImageSharp is fully managed (no native dependency to
  ship in the container), has the cleanest API for this, and its **Six Labors Split License** is free
  for open-source and for organisations under $1M revenue — which is DataBro today. **This is a
  licence to re-check before commercial launch**, and it is the one real liability in this choice.
  Recorded in [STATUS.md](../STATUS.md) rather than left as a surprise.

## Consequences

* Positive: development and production differ by configuration only, so the upload path is exercised
  locally exactly as it runs in production.
* Positive: stored bytes are always ours. The class of attack where a "JPEG" is served back as
  something executable is closed by construction rather than by a validation list that must stay
  ahead of attackers.
* Trade-off: re-encoding loses a little fidelity on already-optimised images and costs CPU on every
  upload. Worth it; an author uploading a screenshot cannot tell.
* Trade-off: the pending window means an image has no `srcset` for a few seconds after upload. The
  API exposes the state instead of hiding it.
* Obligates: re-check the ImageSharp licence before commercial launch; add an SVG decision if vector
  assets are ever required; revisit edge transformation when image traffic justifies a CDN pipeline.
